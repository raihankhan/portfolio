# Architecture Decision Records (ADRs)

ADRs document **significant** technical decisions — the kind where reasonable people would disagree.

## Format

We use the [MADR](https://adr.github.io/madr/) template:

\`\`\`markdown
# ADR-NNNN: Title

## Status

Proposed | Accepted | Rejected | Superseded by ADR-XXXX

## Context

What is the situation? What constraints exist?

## Decision

What did we decide to do?

## Consequences

What becomes easier? What becomes harder?

## Alternatives Considered

What other options did we weigh? Why didn't we pick them?

## References

- Related issues
- External docs
\`\`\`

## Process

1. Open an issue with the **RFC** template
2. Discuss in the RFC until consensus
3. Author the ADR file in \`/content/decisions/\`
4. Link from the relevant projects / case studies
5. Update status as the decision evolves

## Why bother?

ADRs prove **architectural thinking** — the #1 skill FDEs are evaluated on. They're also how teams scale decisions beyond any single engineer's head.
